# 增量材料图谱入库

## 何时使用

当增量材料已经经过正文优先复核并获得“确认入库”授权，而后续工作不应停留在“转 Markdown + 上传文档”，必须完成可供智能体调用的图谱化消化时使用。

适用场景：

- 已有 AI 可读副本，但需判定是否足够完整、是否需要重建或脱敏；
- 多个原件/副本需要以正文证据确定唯一规范承载；
- 需要将材料提炼为执行卡，并挂到检查项证据链；
- 需要将结构化索引同步至 iWiki，同时避免泄露内部参数、联系方式和操作细节；
- 需要把“确认增补入库”台账最终收口为“已入库”。

## 步骤

1. **建立逐条收口台账**
   - 为每条确认材料列出：原件、规范 AI 语料路径、内容质量、脱敏动作、重复关系、执行卡、检查项、iWiki 页面。
   - 先确认材料是新增原件，还是原始候选中已经存在但尚未完成语义消化；后者不应机械增加原始材料总数。

2. **确定规范语料与重复边界**
   - 对正文做 hash 或定向段落差异比对；只有规则主体存在实质差异时才保留平行知识对象。
   - 原件与副本均保留在归档层；AI 语料层只保留一个可检索的规范承载，并在台账说明覆盖关系。

3. **质量收口与最小化脱敏**
   - 先阅读现有 `_AI可读.md`；空壳、OCR 乱码或关键流程缺失时，以原件/OCR 和同批交叉材料重建。
   - 对热线、邮箱、URL、个人信息、内部阈值、系统字段和可被滥用的操作细节实行最小必要保留：优先保留机制和边界，不保留具体可检索值。
   - 流程图的 OCR 不稳定字段不得固化为参数或规则；写为经过核验的流程关系和控制点。

4. **提炼执行卡而非逐文复制**
   - 使用 8 段结构：卡片定位、适用问法、核心判断、关键要点、回答约束、边界与例外、关联卡、来源锚点。
   - 按治理主题合并近似材料，避免一条文件生成一张重复卡。通常可聚合为人工运营、审核闭环、质量评测、异常治理、投诉处置、团队作业或算法链路等主题。

5. **精确挂接检查项证据链**
   - 在检查项证据映射中新增“优先取用”补充表：材料规范承载、对应检查项、执行卡、可证明事实和不得超出证明范围。
   - 不用宽泛的来源批次路由替代正文关联；不夸大材料能证明的范围。

6. **发布 iWiki 结构化索引**
   - 在对应专项父页创建一页“新增材料执行卡与证据挂接说明”，发布治理结论、执行卡索引、检查项关联和现场使用边界。
   - 发布前做敏感信息检查；不上传含个人联系方式、内部风控阈值、模型特征或具体账号处置的内容。
   - 创建后回读页面，确认标题、正文、父级位置和 docid。

7. **收口台账、HTML 与状态文件**
   - 把确认材料状态改为已入库，更新理由为“语料质量收口 + 图谱卡 + 证据映射 + iWiki”。
   - 重新生成全量 HTML 审阅页并校验：行数/卡片数一致，状态计数之和等于总数，搜索和本地链接可用。
   - 更新 SESSION_STATE、当日工作日志和任务状态。

## 关键陷阱

- “已有 Markdown”不等于“已经智能消化”；必须看是否可生成可回答的执行知识和检查项证据。
- 不能用文件名、目录或历史路由直接替代正文相关性判断。
- OCR 只能作为辅助；参数、数量和专有字段识别不稳定时，宁可抽象为控制关系并标明边界。
- 原始材料覆盖数与结构化证据数是不同统计口径，不应因补卡而虚增原始材料总数。
- iWiki 发布的核心是“结构化索引与回答边界”，不是把所有原始材料再次堆放。
- macOS 中文文件名必须通过 Python `os.listdir()` / Unicode NFC 归一化定位，避免 shell 文本匹配静默失效。

## 验证清单

- [ ] 每条确认材料都有规范语料、质量结论、图谱承载和检查项映射。
- [ ] 每个重复结论有正文 hash 或段落差异依据。
- [ ] 重建 OCR 语料保留原始来源和交叉验证来源。
- [ ] 执行卡数量以主题聚合为准，且均含回答约束与来源锚点。
- [ ] iWiki 页面已创建并回读，docid 与父页正确。
- [ ] 全量 HTML 卡片数 = CSV 行数，状态计数之和 = 总数。
- [ ] SESSION_STATE、日记和任务状态已更新。
