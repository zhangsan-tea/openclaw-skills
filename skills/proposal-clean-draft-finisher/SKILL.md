# proposal-clean-draft-finisher

## When to use
在以下场景使用：
- 用户已经围绕方案、制度、汇报稿、管理办法等文稿反复迭代了几轮。
- 前面已经产生过“原文+建议稿”“逐段对照”“修改说明”等中间稿。
- 用户明确表示不要再看对照版，只要一份完整、可直接通读或回贴的建议稿。
- 目标是保留已经确认的结构和有效内容，但去掉分析外壳，让文稿回到“纯正文”状态。

## Steps
1. 先确认当前最新的结构要求和约束，优先使用用户最后一次明确拍板的目录、主轴和边界。
2. 读取最近一版完整稿和必要的中间稿，只提取仍然有效的内容；不要把“调整说明”“原文”“建议理由”带进最终正文。
3. 判断哪些内容属于可复用旧内容：稳定定义、已确认机制、用户认可的表述、能直接落稿的条款。
4. 重新输出一版完整建议稿：
   - 标题清晰；
   - 结构完整；
   - 正文连续；
   - 不出现“原文如下”“建议修改为”“调整说明”等对照语言。
5. 如果用户只要求继续压缩某一部分（如总则、开头、结尾），优先局部改写该部分，其他章节尽量不动；不要因为局部压缩需求又重新展开整篇结构。
6. 当用户要求“形式上更简单”时，优先改成“一段整体概述 + 几个简要段落/短句罗列”的轻量写法，而不是继续细分小标题。
7. 当用户明确觉得文稿“太复杂、太重、架势太大、制度味太浓”时，优先做减法：缩短标题、弱化“管理/考核/激励”等重制度表述，减少固定周期、硬流程、抄送链条、独立大章，让文稿回到“轻量运营、导向为主”的机制口径。
8. 文件名直接体现“完整建议稿 / 纯净版 / final”等状态，避免与对照稿混淆。
9. 如果用户后续要贴回文档或外发，再基于这版继续做格式压缩，而不是回退到对照稿。

## Pitfalls
- 不要把旧的对照结构机械复制成新文件。
- 不要把范围写大，尤其不要把“专项方案”写成“整个团队总纲”。
- 不要为了完整而重新引入用户已经要求弱化的内容，比如重考核、重激励、过度拔高的目标。
- 不要丢掉老方案里仍然可用的机制性内容，如推荐程序、记录方式、动态调整等。
- 用户只要求压缩某一部分时，不要顺手把其他章节也改散，避免再次偏离“只改这一段”的要求。
- 用户已经嫌“形式复杂”时，不要再用多层小标题去重写同一段内容。
- 当用户核心判断是“机制太重”时，不要只做字数压缩；如果标题、章节名、结果运用、激励写法仍然保留强制度感，读感还是会重。

## Verification
完成后自查：
1. 文稿是否可以从头到尾直接阅读，不需要借助对照说明理解。
2. 是否完全去掉了“原文/建议稿/调整说明”等中间态标记。
3. 是否严格按用户最后确认的结构输出。
4. 是否保留了已确认的可用内容，并删掉用户已否定的展开方式。
