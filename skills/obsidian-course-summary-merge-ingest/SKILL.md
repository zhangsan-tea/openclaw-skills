# obsidian-course-summary-merge-ingest

## When to use
- 用户发来一段课程摘要、讲座总结、培训笔记，说“之前好像也学过类似的，帮我看看怎么入库”。
- 用户发来的不是原课内容，而是一个横向比较稿 / 综合分析稿 / HTML 汇总页，需要判断它到底该算新信源、分析 memo，还是未来 topic 骨架。
- 用户发来一篇长文观察 / 内部复盘 / 产品开发运维手记，虽然不是课程，但也要判断它到底该算独立 source、案例型 source，还是从中拆 concept + memo。
- 用户发来团队介绍 / 业务介绍 / 培训型 PPT 解读稿，内容既涉及组织架构，又涉及工作机制、协作链路、线索发现、工具体系等，需要判断它更像“组织情报型 source”还是已有问题线索的补充材料。
- 已有 Obsidian 知识库中很可能存在同主题课程、相同信源、或相邻 concept/topic，需要先比对再决定是否新建条目。
- 重点是避免“同一门课反复新建 source”，同时把真正新增的价值抽到 concept / topic 层。

## Steps
1. 先在项目记忆和 Obsidian 中检索关键词：讲者、课程名、核心概念、关键数据、组织术语。
1.1 如果材料明显在回答项目里一个已持续关注的问题（例如某子团队怎么运作、某模块如何与安全协作），先在项目记忆里定位该问题，再把本次材料当作“问题线索补充”来判断，而不是只按课程摘要处理。
2. 区分三种情况：
   - **同一门课的另一版摘要**：不新建 source，只更新原 source 的表达或补充对照。
   - **不同课程但同主题**：保留各自 source，并把共识/差异抽到 concept 或未来 topic。
   - **全新信源**：新建 source，再决定是否需要更新 concept/topic。
2.1 如果新材料明显是**总纲 / 总览 / onboarding / 纲领性介绍**，并且提纲结构清晰、覆盖主模块、置信度高，优先把它视为该主题下的**高置信锚点 source**：
   - 先沉淀它的提纲骨架（如“定位/任务/队形”），而不是被局部细节带跑；
   - 后续同主题部门介绍、子团队培训、案例稿，优先判断它们是在补哪一层，而不是拿局部材料去重写总纲；
   - 若知识库里已有同主题的二次整合稿，应把这份总纲视为更贴近一手骨架的参照，并在 memo 中说明二者关系。
3. 如果是“同主题的新信源”，再判断它属于哪种补充：
   - **方法论型补充**：更偏组织原则、流程机制、抽象框架
   - **样本型补充**：更偏标杆公司案例、人才流动、外部 benchmark
   - **表达型补充**：事实不新，但表达更顺、适合回写原 source 的措辞层
   - **现场复盘型补充**：带有一手组织现场、产品落地、开发运维、管理秩序、用户反馈的连续观察
   然后决定：是新建独立 source，还是仅更新原 source / concept。
4. 如果输入是一篇长文复盘，额外追问四件事：
   - 它是不是一手现场观察，而不是二手转述？如果是，优先保留独立 source。
   - 它新增的是事实、结构判断，还是只是情绪宣泄？只有前两者值得进 wiki。
   - 它最硬的新抓手落在哪层：产品方法、组织机制、用户研究、研发流程、运维秩序，还是商业竞争？
   - 它是否适合拆成“1个案例型 source + 2-4个 concept + 1篇比较 memo”，而不是把 7 万字都压进一个 source 里。
5. 如果输入本身就是“对多门已入库课程的综合比较稿”，优先先问三个问题：
   - 它有没有提供新的原始事实？如果没有，通常不应新建 source。
   - 它新增的是不是一个可复用的比较坐标系？如果是，优先落到 `wiki/memos/` 作为分析 memo。
   - 当前同主题资料密度够不够？只有密度足够时，才把这类比较稿升级成 topic 骨架。
5. 至少对照三层：
   - `source`：事实、框架、关键数据是否同源
   - `concept`：有没有真正新增的抽象抓手
   - `topic`：是否已达到需要单立主题页的资料密度
6. 如果新材料明显更偏 **AI4SE / 研发组织 / 需求工程 / 测试体系 / 设计驱动**，不要只拿“AI组织进化”这个大框去硬套；要额外检索现有 concept 里是否已有对应的工程型抓手（如 Harness Engineer、结构化需求、可信研发、质量左移）。
   - 如果已有承接概念：优先回写现有 concept
   - 如果没有承接概念：优先采用“新建 source + 新建 1-2 个工程型 concept”的写法，而不是只把它挂到总括型 concept 下面
6.1 如果材料来自**安全 / 风控 / 支付 / 对抗治理**等强业务场景，但真正新增价值落在“如何约束 AI、如何抑制幻觉、如何做测试与发布门禁、如何构造可观测性与闭环自动化”，仍应优先按 **AI4SE / 工程体系新信源** 处理，而不是被业务标签吞掉。
   - 先判断它新增的是业务事实，还是可复用的工程抓手
   - 若工程抓手更硬，source 标题与摘要应突出工程方法，不要只写成行业案例
   - 这类材料常适合采用“1 个场景型 source + 2-3 个工程型 concept + 1 篇比较 memo”
7. 入库时优先做“合并式更新”而不是“复制式新建”：
   - source 层补“与既有课程关系”或“入库判断”
   - concept 层补新增抽象抓手、链接相关 source
   - memo 层承接“横向比较框架 / 综合分析稿 / topic 骨架初稿”
   - topic 层只有在独立信源达到一定密度时再新建
8. 如果新信源提供了一个可复用的结构件（例如“判断力四维”“创始人人才审美”“组织承载条件”），优先把它沉淀成 concept，而不是只堆在 source 里。
9. 如果这次新信源一下子补出了 1-2 个很硬的新 concept，并且知识库里已有相关“总括型”concept，优先采用“新建 source + 新建 concept + 回写总括 concept”的三层写法，而不是把新增判断全压进 source。
10. 输出时必须明确告诉用户：
   - 这次输入属于“重复 / 补充 / 新信源”哪一类
   - 为什么这样入库
   - 具体写到了哪些文件

## Pitfalls
- 不要看到一段新摘要就机械新建一个 source；同源重复会把知识库冲散。
- 对团队介绍 / 业务介绍类 PPT，不要因为它带有培训外壳，就忽略其中的组织情报价值；这类材料常常最值得沉淀的是协作链路、子团队分工、工具接口和前置发现机制。
- 如果它其实是该主题下的总纲 / 总览材料，不要把它和部门剖面稿放在同一层处理；总纲先立骨架，部门稿再补血肉。
- 不要只比较标题；要比讲者、关键数据、核心框架、独特表述是否同源。
- 不要把“表达更顺”误判成“新事实”；这类更适合回写原 source 的措辞层，而不是新开条目。
- 不要把“横向比较稿 / 综合分析稿”误判成新信源；如果它只是重组多门已入库课程，通常应落 memo，不是落 source。
- 不要只因为主题相近就把新材料并回旧 source；如果它补的是“标杆样本 / 人才流动 / benchmark 视角”，通常应作为独立 source 保留。
- 也不要因为同属“AI组织进化”主题，就误把一门新课塞进旧条目；如果它带来的是此前知识线里没有的操作级原则（如 AI Only、AI 作为生产系统、按结果分工、人直接贴问题现场），通常应作为独立 source 进入，再抽 concept。
- 对 AI4SE / 研发组织类课程，不要只把它们当成“AI组织进化”的案例附录；如果新增价值已经落到研发操作系统、需求工程、测试体系、设计驱动等层面，就该给工程型 concept 单独留位置。
- 对安全 / 风控 / 支付这类强业务案例，不要只看到行业外壳；若其真正稀缺之处是“如何把 AI 包进可控工程系统”，应按工程方法论而非行业见闻处理。
- 对长文复盘，不要把作者的文学性、情绪性表述整段搬进 wiki；要抽出可复用的现场判断、结构性张力和方法论抓手，避免把 source 写成散文摘抄。
- 不要只停留在 source 层；真正值得沉淀的新增价值，往往是 concept 层的几个新抓手。
- 只有当同主题独立信源已经形成规模时，才考虑单立 topic；否则 topic 会过早膨胀。

## Verification
- 已明确判断这次输入是重复、补充还是新信源。
- 已说明不新建 / 新建的理由。
- 若执行入库，已列出被更新或新建的 Obsidian 文件路径。
- 没有制造同源重复条目。
