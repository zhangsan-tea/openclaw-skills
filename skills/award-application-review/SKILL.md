# award-application-review

评估企业内部报奖 / 申报材料，站在评委视角挑出"下一版具体要改什么"，而不是罗列优点。核心产物是分优先级的可执行修改意见。

## When to use

- 用户发来一份报奖 / 申报材料（常见为企业微信文档、腾讯文档、飞书文档链接），要求"评估一下""提修改意见""看看能不能中"。
- 用户问"评委会在哪里卡住""为什么这个奖项不合适""怎么改更容易获奖"。
- 常见奖项类型：运营优化奖 / 运营突破奖、技术创新奖、管理创新奖、协作奖等。
- 用户想把一次评估经验沉淀成可复用的评审方法。

不适用：用户只是想让你从零编造项目内容（报奖材料的真实过程、数据只有当事团队有，不能编）。遇到"帮我把过程补出来"的请求，明确说明这部分你编不出来，应交给团队补充。

## 前置：先拿到真实正文

- 若是 `doc.weixin.qq.com` 企业微信文档，通用网页抓取常只返回"企业身份登录"壳。优先用 `wecom-doc-link-reader` skill（`wecom-cli doc get_doc_content`）读正文。
- 飞书文档用 lark 套件，腾讯文档用对应连接器。
- 读正文时**同时留意评论 / 批注**——评论里往往藏着评委或 leader 的真实关切，价值极高，第二轮务必单独提取评论再比对。

## 核心评审框架（七个检查维度）

按此清单逐条过材料，每条落到"下一版要改什么"，不写"这是个很好的观察"。

### 1. 标题：泛主题 vs 具体项目
- 泛主题词（"AI 赋能 XX 治理"）是危险信号——任何同类项目都能套用，评委看不出为什么值得单列。
- 好标题公式：**手段 + 场景 + 差异化结果**。例：从关键词拦截到大模型主动防控——双场景落地的范式跨越。
- 警惕："象是整个团队的长期工作，任何一个进展都能包进来"——报奖应是一个项目或一个特定突破，不是团队年度总结。

### 2. 奖项匹配逻辑：为什么是这个奖，不是那个奖
- 运营优化 / 运营突破奖 强调**流程再造、效率提升、运营范式改变**，主角是"人做了什么让运营变好"。
- 技术创新奖 强调技术本身的新颖性。
- 高频陷阱：一个"造了个模型/系统"的项目报运营奖，全文却在讲技术，评委会觉得报错了奖项。**必须显式回应"为什么是 X 奖而不是 Y 奖"。**

### 3. 叙事弧线：不能只有结果
报奖材料不是 KPI 考核表。完整弧线：
```
痛点（过去怎么做都搞不定，具体到什么程度）
→ 尝试（为什么选这个方向）
→ 落地关键困难（不是有了工具就行，还要克服什么）
→ 突破（做对了什么让效果出来）
→ 结果（量化数据）
→ 长期价值（沉淀了什么资产）
```
只有"结果 + 半个痛点"是最常见的缺陷。挑战、手段、创新点通常最缺。

### 4. 人 vs 工具：功劳归属（引入 AI/新工具类项目的头号杀手）
- 最致命的误解：**"引入了 AI，一切问题就解决了，那团队其实没功劳。"**
- AI / 新工具只提供了可能性，从可能性到落地中间有大量挑战。运营突破奖必须把"团队做了什么把可能性变成战斗力"突出出来。
- 检查主语：如果通篇主语是"模型/系统"（模型链路取代了…、准确率持续提升…），团队就隐身了。要改成"团队做了 X 适配/调优/流程再造，才让工具产生了 Y 效果"。
- 具体可写：能力对齐与标准转化、模型输出对接现有流程、人机协同兜底机制、把判定做到可对外披露证据的程度等。

### 5. 长期价值：落到具体资产
- 不是空写"未来可推广到 XX"，而是问**现在已经沉淀了什么资产**。三选一或组合：
  - 方法论（可复用的标准流程）
  - 模型 / 数据资产（调校后可支撑新需求）
  - 产品 / 系统（换场景只需适配策略层）
- 有资产 = 有长期价值 = 不只是解决一个问题，而是建了持续解决问题的机制。有长期价值的项目比只解一个难题的项目更容易获奖。

### 6. 数据可信度与叙事力
- **削弱性表述必删**："一定程度上""大概""获得点赞"这类词在正式评审语境里自损可信度。
- **孤立数字要给参照系**：如"输出 8 次"——是多是少？评委无法判断。改为对比式："从过去被动应对问询，转为主动系统性输出，累计报送 8 次并获认可。"
- **自嗨数据要翻译**：如"累计运营 47 个事件"——评委不做考核，不知道多少算好。要么删，要么改写成稳定性/覆盖面叙事。
- **统计口径要统一**：同一段落里"专项期间""上半年""周均"混用，评委要停下来算。统一时间口径，或用小表格结构化呈现（指标 / 场景 / 之前 / 之后 / 变化）。

### 7. 申报主体与协同（多部门联合申报时）
- 多部门联合申报，必须回应"为什么是 X 团队牵头""X 在其中不可替代的核心贡献是什么"。不写可能被质疑申报资格。
- 讲清各部门分工，避免评委问"到底谁做了什么"。

## 通俗性检查（易被忽略但常被评论命中）
- 材料常写得"太专业、太策略"，非本领域的评委/leader 看不懂。
- 手段和效果的描述要给出**具象的 before/after 对比**，让外行也能感知价值。
  - 例："过去：收到指令→人工分析→配置规则→生效（T+若干小时）；现在：事件触发→自动适配→分钟级生效。"

## 格式细节 checklist
- 模板提示语（"申报须知：…"）提交前应删除。
- 字数字段（如 300/800 字）粗体混排要统一；剩余字数余量用在补短板（长期价值/奖项匹配），别凑废话。
- "本次申报差异点"字段若留空是失分项：首次申报要写"首次申报"；报过没中要写清本次差异（数据更新、成熟度、新增成果）。

## Steps
1. 拿到真实正文（企微文档走 `wecom-doc-link-reader`）；若有第二版，单独提取新增评论/批注。
2. 用上面七个维度逐条扫描，每条产出"下一版要改什么"。
3. 特别检查两个高频致命项：**功劳归属（人 vs 工具）** 和 **奖项匹配逻辑**——这两条最常被漏，且直接决定能否获奖。
4. 通俗性 + 数据可信度 + 格式细节各过一遍。
5. 输出分层结论，按 **必改 / 建议改 / 可斟酌** 分组，附一句"如果只做 N 件事，优先级是…"。
6. 若有评论，把"我的评估已覆盖 vs 评论新增"对齐成表，避免重复、突出增量。
7. 不替用户编造原稿没有的过程/数据；缺失部分明确标注"需团队补充"。

## Pitfalls
- 不要写大段赞美（"这是个很聪明的方案""让我眼前一亮"）。删掉赞美后干货要 ≥ 赞美。
- 不要用反问式引导（"你是不是应该先想想…"）；直接给判断，以"我"的名义。
- 不要编造材料里没有的落地过程和数据——真实过程只有当事团队有。
- 不要只挑格式小问题而漏掉"功劳归属""奖项匹配"这类决定性的结构问题。
- 整齐的对称数字/结构（4 亮点、3 子项）可能是强行凑数，保持警觉。

## Verification
- 每条意见都能回答"下一版这里具体改成什么"，而非"这个观察有道理"。
- 七个维度都被检查过，尤其"人 vs 工具"和"奖项匹配"未被遗漏。
- 输出有明确优先级分组（必改/建议改/可斟酌）。
- 未编造原稿不存在的事实；缺口标注为"待团队补充"。
