# pdf-to-epub-book-workflow

## Overview
采用“先保字，再保段，再保样式，最后做整书验收”的流程处理中文书籍 PDF→EPUB。优先解决文本完整性和分段正确性，再处理标题/列表样式，避免把坏结构美化成好看的错误结果。

## Entry Rule
- 这是 PDF→EPUB 书籍修复的总入口技能。
- 如果用户只说“这个 EPUB/PDF 有问题了”，但还没分清是分段错还是样式错，先用本技能，再由本技能决定是否下钻到子技能。

## Workflow Decision Tree
1. 先判断问题类型：
   - 若问题是**丢字、断句、跨页丢行、整段被切碎**，优先回到 PDF→EPUB 脚本重做文本重组。
   - 若问题是**标题该加粗没加粗、编号条目误加粗、小标题留白不对**，优先 patch 已有 EPUB，不重跑整条链路。
2. 再判断目标：
   - 追求“可读初版”时，先出可读 EPUB，再做抽样验证。
   - 用户要求“一次性到位”时，必须追加整书自检报告，不能只靠截图回改。
3. 决定产物：
   - 初次生成：`*.epub` + 转换脚本
   - 深度修复：`*.epub` + 自检报告 `*_selfcheck.md`/`*_qc_report.md` + 最终脚本副本

## Recommended Deliverables
- 最终 EPUB：按 `v2/v3/v4/v5/v6` 递增版本号
- 最终脚本：保留 workspace 下可复现脚本副本
- 质检报告：记录风险项、抽样命中、残留例外
- 如用户常在本地设备打开，额外同步到桌面或其指定路径
- 若需远端交付，补一个“可直接下载”的交付通道；对二进制 EPUB，优先保证下载可用，不要只给看起来公开但实际仍会卡权限的文档页

## Core Workflow
1. 读取原始 PDF 和用户截图，先确认问题落在“文本重组”还是“样式分类”。
2. 先盘点版面中的图片：区分“正文插图/图表/装饰页眉页脚/扫描噪声”，默认保留正文插图和图表，剔除明显无信息量的装饰性元素。
3. 生成或读取当前转换脚本，不要盲目在旧结果上补丁。
4. 先做文本完整性验证：
   - 对比 PDF 与 EPUB 的紧凑文本长度
   - 做均匀分布探针或随机探针
   - 重点检查跨页位置、章节开头、后记尾部
5. 若段落切碎，按 @references/reflow-checklist.md 重写段落合并逻辑：
   - 标题保留
   - 编号条目保留为段落开始，不当标题
   - 除标题外，段尾无结束标点默认续接下一行
   - 章节内再做一轮 paragraph-level merge
   - 先做“同页同行短文本合并”，避免表格/对比行被拆成多段后再误判成标题或残句
   - span 级文本拼接要结合 bbox 间距决定是否补空格，尤其要防止中英数字之间粘连或中文被误插空格
6. 若正文中掺杂图片，导出后要按阅读顺序把图片锚到相邻段落之间，避免图片全堆到章首、章尾或单独落成空白页。
7. 若文本完整但样式不对，只 patch 现有 EPUB：
   - 小标题 → `sub-heading`
   - 编号条目 → `list-item`
   - 列表引导句 → `lead-in`
   - 重新打包时保证 `mimetype` 为首项且 `ZIP_STORED`
8. 生成自检报告：
   - 统计 sub-heading/list-item/lead-in 数量
   - 标记 `sub-heading` 风险项（含句读、超长）
   - 标记无结束标点的残留可疑段落
   - 单列“疑似原书少句号例外”
   - 单列图片处理结果：保留数量、剔除数量、是否存在位置漂移风险
9. 如果用户给了截图做二轮返工，把截图当成地面真值：
   - 先在 `*_extracted.txt` 里定位独特短句
   - 再回到解压后的 `EPUB/*.xhtml` 核对具体坏结构
   - 优先把修复写进脚本的 `repair_known_blocks()` / `join_text()` / 分类规则，而不是手改成品
   - 对压平表格、压平列表、标题+正文粘连，优先用“窗口拼接 + 锚点短语命中”重建，不要把规则写死成固定偏移
10. 交付前做三层验收：
   - 结构指标变好：长度差值、可疑段落、可疑小标题不恶化，最好下降
   - 截图命中点修好：用户指出的坏例逐个回查
   - 下载链路可用：附件、文件空间或直链里至少有一个真实可下载入口

## Classification Heuristics
- 章节标题：优先使用 canonical titles/aliases，避免 `1.` 前缀丢失造成误判。
- 小标题：使用“短文本 + 上一段正常结束 + 下一段像正文”的组合判断；不要只靠长度。
- 编号条目：`一、/（一）/1.` 等默认视为正文条目，不视为标题。
- 列表引导句：通常以 `：` 结尾，且下一段应为编号条目。
- 表格/对比行：若同一视觉行内存在 3 段及以上短文本、且末尾无完整句读，优先按表格行处理，不要直接并入前后正文。
- 对压平后的表格/对比块，不只看单行；要允许向后拼接 6-12 行窗口，再用列名/锚点短语判断是否重建成表格。
- 流程行：含 `→/->` 的链式表达优先视为流程或结构行，不要按普通段落续接。
- 短独立标题：对 22 字以内、无句读的独立行，要结合居中程度、下一行缩进和下一行类型一起判断，避免把短残句误升格成标题。
- 中英数字混排：`join_text()` 既要防粘连，也要防误插空格；中文→英文、英文→中文、数字→中文这几类边界都要显式处理。

## Pitfalls
- 不要一上来就调 CSS；若结构错了，样式越调越乱。
- 不要把“视觉折行”误当“作者换段”；中文 PDF 尤其容易在无句号处误切。
- 不要把编号条目误判为小标题；这会导致条目正文继续被拆断。
- 不要把表格/对比行先拆碎再做段落合并；应先按同行聚合，否则很容易在报告里堆出大量假阳性残句。
- 不要忽略 span 间距；中英数字混排时，不补空格会粘词，乱补空格会伤中文可读性。
- 不要把所有无句号段落都强行改写；极少数可能是原书本身少句号，应在报告中留痕。
- 不要只做局部页检查；必须做整书级验证，否则尾部问题很容易漏掉。
- 若用户已经给出硬规则，优先把规则写进脚本，而不是靠人工记忆反复微调。
- 不要把压平表格的修复写死成 `i+1/i+2/i+8` 这类固定偏移；PDF 重排一变，规则就失效。
- 不要把正文插图和扫描噪声一股脑全保留；图片要先分型，再决定保留与否。
- 不要只检查图片有没有导出成功；还要检查它是否落在正确段落附近，避免阅读顺序错位。
- 不要把腾讯文档文件页“看起来能打开”误判为真正公开；二进制文件常出现权限策略回读未生效的情况，交付时要额外验证下载链路。

## Verification
- 文本完整性：紧凑文本长度差异可解释，关键探针命中。
- 分段正确性：残留疑似误分段为 0 或极低，且例外有单独说明。
- 样式正确性：真正小标题加粗留白，编号列表不误加粗。
- 图片处理正确：正文插图与图表已保留在合理位置，装饰性噪声未污染正文阅读流。
- 用户截图中的典型坏例必须回查并修复，例如“一个攻 / 击”“一个僵化 / 而干瘪的能量球”。
- 交付前附上 EPUB + 报告 + 脚本，避免下次从零排查。
- 若用户要求云端下载，必须亲测至少一个链接是真能下载文件，而不是只返回文档详情页。
